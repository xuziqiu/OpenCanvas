# OpenCanvas 产品交付完整度审计

审计日期：2026-09-06<br>
目标版本：1.0.10<br>
范围：单机、个人、本地优先的 Windows 视觉知识工作区。

## 结论

OpenCanvas 已具备“可以长期保存真实个人资料”的核心闭环，但“功能做成”不等于“产品交付完成”。1.0.10 在完整用户手册之外补齐首次引导、诊断、反馈、GPL-3.0-only 许可、第三方许可证清单、依赖安全门禁和公开前来源清理，可作为**公开测试版候选**交付；要把它称为面向普通用户的公开稳定版，仍需完成升级/降级策略和真实设备/真实资料矩阵。当前选择暂不购买代码签名，因此公开分发时必须保留“未知发布者”说明和 SHA-256 校验值。

## 正式稳定版之前的门槛

### P0：没有完成就不应称为公开稳定版

1. **真实资料终验**：至少一份真实 Heptabase 导出、一个含大量附件的知识库、一个旧格式知识库、一个 OneDrive 或同步盘路径。
2. **升级与降级策略**：升级前备份；明确哪个版本写入后不能由旧版本继续编辑；迁移失败可恢复。
3. **公开发布验收**：明确展示当前安装包未签名，发布 SHA-256，并从全新 Windows 账户完成下载安装验收；若未来面向非技术用户广泛分发，再评估代码签名。

### P1：私有预览可继续迭代，但应排入近期版本

1. 首次引导后的情境提示：第一次框选、第一次多选、第一次连线、第一次导出时只提示一次。
2. 自动或提醒式备份，并可查看最近一次成功备份时间。
3. 辅助功能人工矩阵：键盘、屏幕阅读器、系统 200% 缩放、减少动态效果、高对比度。
4. 把当前 CI 质量门禁扩展为受保护的发布流水线：安装/便携 smoke、校验和和 Release 说明；代码签名作为可选阶段。
5. 应用内更新检查与发布通道；在用户明确同意前不自动联网。
6. 根据真实反馈持续校正问题模板与诊断字段。

### P2：公开扩张前再决定

- 多语言、公开官网、公开路线图、插件 API、移动端、云同步、多人协作、PDF 标注。
- 这些不是当前个人本地工作区的交付阻塞项，不应抢占数据可靠性和核心交互打磨。

## 每次发布的完成定义

一个版本只有同时满足以下条件，才算“完成”，而不是“代码已经改完”：

1. 用户任务和不做什么已经写明。
2. 交互、数据格式、迁移和失败路径均有验收标准。
3. 自动测试通过，高风险路径完成真实 Electron 或安装包测试。
4. 手册、快捷键、开放格式和版本说明与功能同步。
5. 安装、升级、退出、卸载、恢复、导入和导出都有明确结果。
6. 发布物有版本号、校验和、已知限制和回滚方式。
7. 没有把未做过的真实设备或真实资料测试描述为已经通过。

## 建议的后续顺序

1. 先做升级前备份、迁移策略和真实资料矩阵，封住数据风险。
2. 把现有 CI 扩展到受保护的发布流程，并自动生成校验和、许可证清单和 Release 说明。
3. 在用户群扩大、SmartScreen 摩擦明显时，再配置可信代码签名。
4. 最后再考虑需用户明确同意联网的更新检查、国际化和公开发布。
